## 3. 关键实现要点

### 3.1 高频 tick：直接改 `textContent`

没有框架就没有 diff 开销，计时数字每秒更新就是一行：

```ts
// ui/render.ts：一个 rAF 循环，收集脏回调后统一执行
const dirty = new Set<() => void>();
export function schedule(fn: () => void) {
  dirty.add(fn);
}
function frame() {
  dirty.forEach((f) => f());
  dirty.clear();
  requestAnimationFrame(frame);
}
requestAnimationFrame(frame);

// ui/components/timer-display.ts
const el = document.querySelector("#remain")!;
engine.onTick(({ remainMs }) =>
  schedule(() => {
    el.textContent = format(remainMs);
  }),
);
```

### 3.2 Web Components 用法边界

**只在"有独立内部状态 + 会复用"的地方用自定义元素**：`<timer-display>`、`<free-debate>`、`<prompt-overlay>`。
**一次性布局（页头、控制条、设置面板）直接写在 `index.html` 里**，由 `main.ts` 查询元素并绑定事件即可——不必为 5 个按钮套一层自定义元素。

### 3.3 DOM 构建一律用安全 API

列表渲染只接受内部数据，仍统一用 `createElement` + `textContent` / `replaceChildren`，**不使用 `innerHTML`**，避免把辩题、环节名这类用户可编辑文本变成注入面。

### 3.4 `core/` 完全相同

引擎、提示点预算时间戳、时钟校准、数据模型与 A/B **逐字共用**（纯 TS，零依赖），因此单测策略一致，且未来从 C 迁到 A/B 时 `core/` 一行不用改。

### 3.5 样式：原生 CSS 还是 Tailwind？

| 选项                                   | 优点                     | 缺点                     |
| -------------------------------------- | ------------------------ | ------------------------ |
| **C-1：原生 CSS + tokens.css（推荐）** | 真正零构建依赖，产物最小 | 要自己维护样式体系       |
| **C-2：Tailwind 4.3.3**                | 与 A/B 一致、写起来快    | 名写在模板字符串里略啰嗦 |

本项目只有 2 个页面（主屏 + 设置/编辑面板），手写 CSS 完全可控，推荐 C-1；若希望三方案样式体系统一、方便日后切换，选 C-2。

### 3.6 赛制编辑器（C 方案唯一的痛点）

环节列表要支持「增删 + 上移下移 + 改时长 + 改提示点」。环节数少（<20），**全量重建列表**即可：

```ts
function renderStageList(stages: Stage[]) {
  listEl.replaceChildren(...stages.map((s, i) => stageRow(i, s)));
}
```

代价：重建会让正在编辑的输入框失焦。规避：**只在"增删/排序"时重建列表；编辑名称/时长时走受控输入，不重建**。

动效用 CSS：`@keyframes` 做提示横幅滑入、数字颜色用 `transition: color 200ms`、控制条 `opacity` 过渡。

## 5. 里程碑（C 方案）

| 阶段 | 内容                                                         | 完成判据                                          |
| ---- | ------------------------------------------------------------ | ------------------------------------------------- |
| M0   | `npm create tauri-app@latest`（选 Vanilla + TS）→ 空全屏窗口 | `npm run tauri dev` 起窗                          |
| M1   | `core/` 引擎 + Vitest 单测                                   | 单测：暂停恢复不丢时、提示点不漏、休眠校准、±加时 |
| M2   | 主屏（index.html + 少量自定义元素）                          | 单环节可跑，辩题可改                              |

| M4   | 赛制编辑器 + 导入导出 JSON                                   | 新建赛制，重启后仍在                              |
| M5   | 快捷键 + 设置面板 + 打磨 + 三平台打包                        | 三平台有安装包；输入框聚焦不误触发                |

## 6. C 方案特有风险

| 风险                               | 对策                                                             |
| ---------------------------------- | ---------------------------------------------------------------- |
| 列表编辑器状态管理啰嗦             | 环节数 <20，增删/排序时重建、编辑时不重建（§3.6）                |
| 手写无障碍（焦点陷阱、aria）成本高 | 弹窗只有 2 个（设置、编辑辩题），按需加 `aria-label` 与焦点管理  |
| 没框架反而容易写出一个迷你框架     | 明确禁止；只保留 `store.ts`（约 40 行）+ `render.ts`（约 15 行） |
| 团队接手时不知从何下手             | `core/` 与 A/B 共用且是主要逻辑，UI 层代码量不大                 |

---

## 7. 选 C 的理由 / 不选 C 的理由

**选**：想要极致小的产物、最快的启动（老旧多媒体电脑），以及"十年后打开还能跑、不被框架版本牵着走"。
**不选**：赛制编辑器这类交互在无框架下更费手；若后期要大量扩展 UI，A 或 B 更省力。

---

## 8. 与 A/B 的迁移成本

`core/`（models / engine / clock / presets / storage / audio / hotkeys）三方案**逐字相同**：
**C → B 或 C → A 只需重写 `ui/` 层**，`core/` 与全部单测可直接复用。这是本方案"低风险试错"的价值。
