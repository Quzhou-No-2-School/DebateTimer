# DebateTimer 测试与 CI 实施计划

> **For Claude:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task.

**Goal:** 给 DebateTimer 建四道自动化闸门——代码格式检查、单元测试、e2e 测试、编译检查——其中 e2e 与编译检查在 Windows（10 世代 / 11 世代 / 真 Win11 arm64）、Ubuntu Linux、macOS 上各跑一遍。

**Architecture:** 两条流水线。`quality` 是 Linux 单机快速道（格式 + 类型 + 单测），PR 上几十秒出结论；`platform` 是平台矩阵道（编译检查 + 真实桌面 e2e），三平台阻塞、两个探测行非阻塞。e2e 用 WebdriverIO 的 **embedded provider**（WebDriver 服务跑在应用进程内），因此 Windows / Linux / macOS 三平台同一套配置、无外部 driver、无付费 key。

**Tech Stack:** Tauri 2.11 · Svelte 5.56（runes）· SvelteKit 2.65 + adapter-static（SPA）· TypeScript 6.0 · Vite 8.0 · Tailwind 4.3 · Vitest 3.2 · Prettier 3.9 + prettier-plugin-svelte 4.1 + prettier-plugin-tailwindcss 0.8 · `@wdio/tauri-service` 1.4 + `tauri-plugin-wdio-webdriver` 1.4 · rustfmt/clippy · npm（**pnpm 本机不可用**）· GitHub Actions

## 1. 与既有项目约束的衔接

- **三平台完全同等**（`memory: project_debatetimer`）：所以三平台都必须跑 e2e，不能只跑 Windows。
- **全屏应用必须有退出入口**（`memory: feedback_quit_entry`）：退出路径必须被 e2e 覆盖，这是已验收过的功能点，不能回归。

## 2. 平台映射：为什么是这三个 Windows runner

这是本计划里唯一需要"如实告知缺口"的地方，先讲清楚再动手。

**硬约束：GitHub 托管 runner 不存在真 Windows 10 / Windows 11 的 x64 镜像。** 已核实的可用集合是 `windows-2022`（=Windows Server 2022，内核 10.0.20348）、`windows-2025` / `windows-latest`（=Windows Server 2025，内核 10.0.26100）、`windows-11-arm` / `windows-11-vs2026-arm`（字面 Windows 11，但 arm64）。来源：[GitHub-hosted runners reference](https://docs.github.com/en/actions/reference/runners/github-hosted-runners)、[actions/runner-images README](https://github.com/actions/runner-images)。

**已排查过的社区替代方案（均不采用，理由如下）**

- **其他托管 CI**：Azure Pipelines / AppVeyor / CircleCI / Cirrus CI / Buildkite / TeamCity Cloud 全部只提供 Server 镜像；SourceHut 连 Windows 都没有。GitHub larger runner 的自定义镜像也只能基于 GitHub 自有 Server 基底，不能自带 Win10/11 ISO。→ 无解。
- **`dockur/windows`（容器里跑真 Win10/11 VM）**：需要宿主暴露 `/dev/kvm`。GitHub 官方对标准 Linux runner 的立场是"技术上可行但不受支持、实验性、无 SLA"（[runner-images#7670](https://github.com/actions/runner-images/issues/7670)），且 `ubuntu-26.04-arm` 上已确认缺失（[#14549](https://github.com/actions/runner-images/issues/14549)）。该项目的 README 明确要求 `--device=/dev/kvm`，并且**找不到任何一份已公开跑通的 GitHub Actions workflow**。冷启动需完整安装 5–8GB ISO，量级 15–40 分钟。此外 Win11 客户端虚拟化在许可上需要 VDA / Enterprise（[微软授权指引](https://www.microsoft.com/licensing/guidance/Windows-11-Licensing-for-Virtual-Desktops)）。→ 判定为实验级，不进主流水线。
- **自建 runner 挂真 Win10 机器**：字面满足度最高，但官方**没有**"可选 / 非阻塞 job"机制——job 排队时若 runner 离线，会**挂满 24 小时才被自动取消**（[limits 文档](https://docs.github.com/en/actions/reference/limits)）。→ 本次不采用，但保留为后续可选扩展（见 §7）。

**采用的映射（诚实标注）**

| runner           | 对应真实环境                 | 在矩阵里的角色                               |
| ---------------- | ---------------------------- | -------------------------------------------- |
| `windows-2022`   | Windows 10 世代内核 + WOW64  | **主 Windows e2e**，阻塞 PR                  |
| `windows-2025`   | Windows 11 世代内核          | 编译检查阻塞；e2e 作为**非阻塞探测**（见下） |
| `windows-11-arm` | **字面 Windows 11**（arm64） | 非阻塞探测，实验性                           |

> ⚠️ **必须写进 README 的缺口**：以上三个都不是普通用户的 Windows 10 / 11 消费版桌面。测不到的东西包括：消费级 WebView2 版本差异、DPI 缩放、Windows Defender / SmartScreen 拦截、非管理员权限运行。这些仍须保留一份**手工验收清单**。

**关于 `windows-2025` 上到底能不能跑 e2e：两条冲突证据**

- [actions/runner-images#14738](https://github.com/actions/runner-images/issues/14738)（2026-09-16 提交，**仍 open**）：`tauri-driver` + `msedgedriver` 在 `windows-2025-vs2026` 上确定性失败 `DevToolsActivePort file doesn't exist`，同 commit 在 `windows-2022` 上 8/8 通过。
- [webdriverio/desktop-mobile#542](https://github.com/webdriverio/desktop-mobile/issues/542)：根因更普适——GitHub runner **以管理员身份运行**，Edge 150+（2026-07 起）在该条件下丢失 `--remote-debugging-port`，wry 的上游修复被拒。受影响的是经 CDP 的 `official` / `crabnebula` provider；**embedded provider 不走 CDP，免疫此问题**。

结论：既然我们选 embedded provider，#14738 未必适用于我们。但"未必"不是"确定"，所以 `windows-2025` 上的 e2e 先做成**非阻塞探测**收集证据，跑绿若干次后再提升为阻塞（§5 Task 12）。

> 同一发现也意味着：**Tauri 官方那份 [WebDriver CI 文档](https://v2.tauri.app/develop/tests/webdriver/ci/) 已经过时**——它教的是 `tauri-driver` + `msedgedriver`，在所有 GitHub Windows runner 上都已失效，而且完全没覆盖 macOS。不要照抄那份 workflow。

## 3. 四道闸门定义

| 闸门           | 命令                                                                                      | 跑在哪                                 | 说明                                                               |
| -------------- | ----------------------------------------------------------------------------------------- | -------------------------------------- | ------------------------------------------------------------------ |
| ① 代码格式检查 | `npm run format:check` + `cargo fmt --check` + `cargo clippy -D warnings`                 | Linux 单机                             | clippy 归在这一道（它是"代码规范"而非"能编译"）                    |
| ② 单元测试     | `npm test`（vitest run）+ `cargo test`                                                    | Linux 单机                             | 当前 vitest 31 个用例全绿（已实测）；Rust 侧目前零测试，命令先接上 |
| ③ e2e          | `npm run test:e2e`                                                                        | ubuntu-24.04 / windows-2022 / macos-15 | WebdriverIO + embedded provider                                    |
| ④ 编译检查     | `npm run check`（svelte-check）+ `npm run build`（vite）+ `npm run tauri build`（真打包） | 五平台矩阵                             | 逐平台真打包才算"平台编译通过"                                     |

### 3.1 ⚠️ `frontendDist` 缺失会 panic —— 但被 feature 门住（2026-09-22 实测更正）

> 本节原来的判断是"`cargo check` / `cargo clippy` / `cargo test` 三者都必须在 `npm run build` 之后运行"。
> **Task 6 的实测推翻了这一条**，以下是更正后的结论。

`src-tauri/tauri.conf.json` 里 `frontendDist: "../build"`，`tauri-codegen` 展开 `tauri::generate_context!()` 时确实会检查该目录是否存在，不存在就 panic：

```rust
// tauri-codegen 2.6.3 src/context.rs:187-190
if !assets_path.exists() {
    panic!("The `frontendDist` configuration is set to `{path:?}` but this path doesn't exist")
}
```

**但这个检查只在"非 dev"编译路径上才会走到。** 同一文件 `src/context.rs:178`：

```rust
} else if dev && config.build.dev_url.is_some() {
    // 用空 EmbeddedAssets：前端产物一个都不嵌入，frontendDist 的存在性也不检查
```

而 `dev` 不由 profile 决定，由 **feature** 决定（`tauri-macros 2.6.3 src/context.rs:155`）：

```rust
dev: cfg!(not(feature = "custom-protocol")),
```

本项目 `src-tauri/tauri.conf.json:8` 已配置 `"devUrl": "http://localhost:1420"`，于是：

| 命令                                           | 是否启用 `tauri/custom-protocol` | `build/` 缺失时                   |
| ---------------------------------------------- | -------------------------------- | --------------------------------- |
| `cargo check` / `clippy` / `test`              | 否 → `dev = true`                | **通过**（走 178 行分支跳过检查） |
| `cargo check --features tauri/custom-protocol` | 是 → `dev = false`               | **panic**（exit 101）             |

**实测记录（2026-09-22，本机 Linux，Tauri 2.11.6）**

```bash
mv build /tmp/dbt-build-backup
npm run check:rust     # EXIT=0  ← 原预期为失败
npm run lint:rust      # EXIT=0
npm run test:rust      # EXIT=0, test result: ok. 0 passed
cargo clean -p tauri-app && npm run check:rust   # 仍 EXIT=0（Removed 743 files / 3.3GiB），排除增量缓存干扰
cargo check --features tauri/custom-protocol     # EXIT=101，复现出 frontendDist panic
```

**结论**

- `cargo check` / `clippy` / `test` **不需要** `npm run build` 前置。`quality.yml` 不会因为全新 clone 缺 `build/` 而炸。
- panic 仍然真实存在，只在启用 `tauri/custom-protocol` 的构建里触发——即 `tauri build`。而 `tauri build` 会先执行 `beforeBuildCommand: npm run build`，顺序自动满足。
- 所以「build 必须先于 Rust 命令」**不是承重约束**。`verify` 脚本继续保留，但它的价值是"一条命令跑完全部闸门"的便利聚合，**不是**规避 frontendDist panic。
- ⚠️ 若日后把 `devUrl` 从 `tauri.conf.json` 移除，178 行的分支不再命中，本节结论立即失效——那时 `cargo check` 会在缺 `build/` 时 panic。

#### Task 2: 接入 Prettier，先量出改动规模

**Files:** Create `.prettierrc.json`, `.prettierignore`; Modify `package.json`

**Step 1:** 安装（版本已核实：`prettier` 3.9.8 / `prettier-plugin-svelte` 4.1.1 / `prettier-plugin-tailwindcss` 0.8.1）

```bash

```

> `prettier-plugin-svelte` v4 **只**支持 Prettier 3 与 Svelte 5+，与本项目匹配（[插件 repo](https://github.com/sveltejs/prettier-plugin-svelte)）。`prettier-plugin-tailwindcss` **没有 v4**，最新就是 0.8.x，它通过 `tailwindStylesheet` 支持 Tailwind 4 的 CSS-first 配置（[插件 repo](https://github.com/tailwindlabs/prettier-plugin-tailwindcss)）。

**Step 2:** 创建 `.prettierrc.json`。**插件顺序有硬要求：`prettier-plugin-tailwindcss` 必须放最后**（该插件 README 明确要求，并显式列出与 `prettier-plugin-svelte` 的兼容）：

```json
{
  "plugins": ["prettier-plugin-svelte", "prettier-plugin-tailwindcss"],
  "overrides": [
    { "files": "*.svelte", "options": { "parser": "svelte" } },
    { "files": "src/core/presets.ts", "options": { "printWidth": 140 } }
  ],
  "tailwindStylesheet": "./src/app.css",
  "printWidth": 100,
  "semi": true,
  "singleQuote": false,
  "trailingComma": "all"
}
```

> `printWidth` 全局定为 **100**，只给 `src/core/presets.ts` 单独覆盖成 140（2026-09-22 拍板）。
> 原因：`presets.ts` 里的内置赛制是一张“一个 `stage({...})` 一行”的数据表，宽度 100 会把每条拆成 ~7 行（221 → 531 行），把这张表的可扫读性彻底毁掉；单独覆盖成 140 后该文件仍是 222 行，表格形态原样保留。
> 但全局 140 会反过来伤到别处——`src/components/TimerDisplay.svelte` 里两个含嵌套三元、本就该多行的 `$derived` 表达式会被压成正好 140 字符的单行。所以取“全局 100 + 单文件覆盖 140”的组合：两种文件各自的形态都保住。
> 两个 override 不重叠（`*.svelte` 与单个 `.ts` 文件），`prettier-plugin-tailwindcss` 仍排在 plugins 末位。

**Step 3:** 创建 `.prettierignore`：

**写测试前必读的 3 个坑（都已读源码确认）**

1. **控制条 3 秒后淡出**：`src/routes/+page.svelte:30` 里 `setTimeout(() => (controlsVisible = false), 3000)`。淡出只改 `opacity-0`，元素仍在 DOM 里、仍可点击，但视觉断言会翻车。**每次操作前先 `await browser.$('main').moveTo()` 唤回**（`wake()` 绑定在 `onmousemove` / `onpointerdown`）。

describe("计时核心", () => {
  async function wake() {
    await $("main").moveTo(); // 唤回淡出的控制条

  it("空格开始后按钮变为「暂停」", async () => {
    await wake();
    await browser.keys(["Space"]);
    await expect($("button=暂停")).toBeDisplayed();
    await browser.keys(["Space"]); // 还原成暂停态，避免影响后续用例
  });

  it("按 Enter 进入下一环节", async () => {
    await wake();
    const before = await $(".tnum").getText();
    await browser.keys(["Enter"]);
    await browser.pause(300);
    const after = await $(".tnum").getText();
    expect(after).not.toBe(before);
  });

  it("重置把剩余时间还原", async () => {
    await wake();
    await browser.keys(["Space"]);
    await browser.pause(1500);
    await browser.keys(["Space"]);

    await browser.pause(300);

        with:
          node-version: 22
          cache: npm

      - uses: dtolnay/rust-toolchain@master
        if: ${{ !matrix.main_only || github.event_name == 'workflow_dispatch' || github.ref == 'refs/heads/main' }}
        with:
          toolchain: 1.98.0
          components: rustfmt, clippy

### 6.3 CI 成本与缩量开关

Tauri 官方文档提到未缓存的冷启动 `create-tauri-app` 项目构建约 **1 小时量级**（[Tauri 流水线文档](https://tauri.app/distribute/pipelines/github/)）；x64 原生 runner 的具体耗时官方没给数字，**未能确认**，实际以首次跑通的数据为准。

用户已明确要 PR 上跑三平台全量 e2e。若日后觉得 PR 反馈太慢，按代价从低到高依次缩：

1. 把 `windows-2025` 编译行挪到 main-only（省 1 次 Windows 全量打包）
2. 把 e2e 的 `tauri build` 从全量打包改成 `npm run test:e2e:build`（`--no-bundle`，跳过 bundler，省最多时间）
3. `macos-15` 的 e2e 改成 main-only
4. 如上仍不够，退到"PR 只跑 Linux e2e"

> 第 2 条其实可以**立即**用在阻塞行上：`--no-bundle` 已经足够证明"能编译"，而打包（deb/msi/dmg）留到 release 流水线再做。当前计划让阻塞行跑全量 `tauri build` 是为了顺带把打包也验证掉；若耗时不可接受，这是第一个该动的地方。
>
> **已于 2026-10-01 落地**：Windows `light.exe` / macOS `bundle_dmg.sh` 在托管 runner 上不可靠（编译成功但打包必败、内部错误不透出），PR 阻塞行已改为 release `--no-bundle`（windows-2025 整行实测 4m56s），msi/dmg 验证留待 release 流水线。

### 2026-10-01 CI 实测结论（PR #5，runs 36872346060 / 36874548218 / 36880425327）

§7 四个未决项全部闭合，证据均来自 GitHub Actions 真实运行（全程未本地跑测试）：

| 项                          | 结论                       | 证据                                                                               |
| --------------------------- | -------------------------- | ---------------------------------------------------------------------------------- |
| macOS 签名 / TCC            | 不需要                     | macos-15 e2e 绿，无任何签名/TCC 配置                                               |
| `browser.keys()` 平台一致性 | 三平台一致，无需退化为点击 | 接通插件栈后（36872346060）键盘用例即全绿                                          |
| `withGlobalTauri: true`     | 需要（仅 e2e/debug）       | 缺它则每条命令 5s "core.invoke not available" 超时；e2e 构建经 tauri.e2e.json 开启 |
| `tauri-plugin-wdio`         | 需要                       | 同上；Rust 侧 debug 门控 + 前端 JS 仅 e2e 模式加载                                 |

附带两个此前未记录的 embedded provider 行为（三轮 CI 才定位，后续 e2e 务必记住）：

1. **单 App 实例跨 spec session 复用**：`quit()` 的 `stopLoop()` 会冻结 RAF 时钟、localStorage 持久，后续 spec 会吃到脏状态（36874548218 的 timing 假红）。spec 必须自清理（reload），不能依赖"每个 spec 拿到新 App"。
2. **spec 内不能真杀进程**：应用退出会连带杀死 embedded WebDriver，WDIO 的 deleteSession 报 ECONNREFUSED，spec 被标记失败——成功也红、回归反而绿。退出路径断言用 `onCloseRequested` + `preventDefault()` 拦截（见 `e2e/specs/quit-confirm.e2e.ts`）。

打包遗留：Windows `light.exe` / macOS `bundle_dmg.sh` 在托管 runner 上不可靠且内部错误不透出，PR 阻塞行已改 release `--no-bundle`（§6.3 第 2 条落地），msi/dmg 验证留给 release 流水线。

### 后续可选扩展（本次不做）

- **自建 runner 挂真 Windows 10 机器**：唯一能字面覆盖真 Win10 的方案。做法是**单独一个 workflow**（不要并入 `platform.yml`），且**绝不设为 required check**——官方没有非阻塞 job 机制，runner 离线时 job 会排满 24 小时才被取消（[limits](https://docs.github.com/en/actions/reference/limits)），设成 required 会直接卡死所有 PR。
